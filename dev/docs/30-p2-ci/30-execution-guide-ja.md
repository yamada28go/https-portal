# HTTPS-PORTAL P2 実施手順

用途：P2の進め方の概要。P2-01は検証成功・完了。P2-02のCI移管は未着手。
[文書一覧](../00-index-ja.md) / [詳細計画](31-implementation-plan-ja.md)

## 目的

既存テストをGitHub Actionsで自動実行し、変更による不具合をPRの段階で検知できるようにする。

## 実施する順番

**① 現状の再現 → ② 単体テストのCI化 → ③ Docker試験基盤 → ④ 結合試験の追加 → ⑤ 安定性確認・必須チェック化**

各段階の完了条件を確認してから、次へ進む。

| 順番 | 段階 | 実施すること | 完了条件 | 目安 |
|---|---|---|---|---|
| 1 | 現状の再現（P2-01） | 現在の変更内容を確認する。CI用の最小Ruby環境を作り、既存113例とMutation検証を実行する | 既存テストが成功し、故意に入れた変更を検知できる。実行したコードのバージョンと結果が記録されている | 0.5〜1日 |
| 2 | 単体テストのCI化（P2-02） | GitHub Actionsにlint-and-unitを追加する。Ruby構文・既存テスト・Mutation検証を自動実行する | PR・push・手動で実行できる。正常なら成功し、故意の変更では失敗する。結果を確認できる | 0.5日 |
| 3 | Docker試験基盤（P2-03） | 試験専用ネットワーク・コンテナ・ボリュームを用意する。起動待機の期限、ログ収集、後片付けを実装する | 公開DNS・公開ACMEに依存せず起動する。個別・繰り返し実行ができ、失敗時も期限内に終了して原因を確認できる | 1〜1.5日 |
| 4 | 結合試験の追加（P2-04） | 実際のHTTP/HTTPS通信で、配信・転送・認証・証明書・永続化を検証する | 下記の主要項目が成功し、誤ったCA・ホスト名などの異常も検出できる | 1〜1.5日 |
| 5 | CI接続・必須チェック化（P2-05） | GitHub Actionsにdocker-smokeを追加する。同じ基準コミットで5回連続成功を確認し、両ジョブをマージ必須条件に設定する | PRで自動実行され、失敗するとマージできない。再実行とログ確認の手順が文書化されている | 1〜1.5日 |

合計の目安は **4〜6.5人日＋レビュー・CIの待ち時間**。古いRuby環境の構築やGitHubの設定権限の調整で増える場合がある。

## 段階4で確認すること

| 項目 | 確認内容 |
|---|---|
| HTTPS起動 | 空の試験用ボリュームから自己署名証明書を作り、HTTPSで正常なページを返す |
| HTTPリダイレクト | HTTPからHTTPSへ301を返し、パス・クエリを維持する |
| リバースプロキシ | 試験用アプリへ正しく転送し、Hostや転送ヘッダーを維持する |
| Basic認証 | 未認証・誤認証は401、正しい認証は200になる |
| 証明書 | 試験用CAで検証に成功し、誤CA・誤ホスト名では失敗する。証明書と鍵が一致する |
| 永続化 | コンテナを再作成しても、保存した証明書を引き続き使用する |
| 更新スキップ | 有効期限が十分残る証明書を、不必要に更新しない |
| 静的配信 | 試験用のindexと別パスが期待どおりの内容を返す |

強制更新には現行コード上の懸念があるため、正常な更新を保証したことにはせず、別途調査する。

## 繰り返し実行と外部への影響

計画どおりの隔離を実装し、受入試験で確認する。

| 対象 | 方針 |
|---|---|
| 公開DNS | レコードを作成・変更しない。試験用の名前をDocker内部で解決する |
| Let's Encrypt | 証明書の発行要求を送らない。自己署名・試験用CAを使う |
| 公開中サービス | 試験専用の構成・データを使い、変更を加えない |
| イメージ公開 | P2ではレジストリへ公開しない |
| 準備時の外部通信 | イメージ・OSパッケージ・Gem・Action等の取得が発生する |
| GitHub Actions | コード取得、結果・診断ログ保存、実行枠・ストレージ消費が発生する |
| 試験実行中 | 単体テストはネットワーク無効。結合試験はDocker内部の試験専用通信に限定する |

試験用データは実行ごとに分離し、後片付けする。永続化試験の中だけ、同じボリュームを意図的に再使用する。秘密鍵・資格情報はログや成果物に含めない。

## 進め方のルール

- 最初は段階1から着手する。
- 各段階をレビュー可能な変更単位に分ける。
- 既存の作業内容を保持し、開始時点の状態を記録する。
- 依存バージョン更新や製品の動作変更を混ぜない。
- テストの失敗を、期待値の安易な書き換えや再試行だけで隠さない。
- 5回連続成功にはキャッシュなし実行とworkflow再実行を含める。問題を修正した場合は、その後に数え直す。
- GitHubの必須チェック設定と、失敗時にマージを阻止できることまで確認してP2完了とする。
